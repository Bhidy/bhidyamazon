# Amazon Egypt — Free/Scraping Research Findings


## amazon.eg Best Sellers and Movers & Shakers as free/scrape targets — URL patterns, locale, browse-node tree, fields, pagination, refresh cadence, parsing approach

*Confidence: medium*

amazon.eg exposes the standard Amazon "zeitgeist" (p13n) ranking pages at /gp/bestsellers and /gp/movers-and-shakers, mirroring the amazon.ae/amazon.com layout (page templates even self-label "amazon.ae" — Egypt runs on the shared MENA platform). Each list is server-rendered HTML in a p13n-desktop-grid, ~50 ranked items per category split across 2 pages (top 100) where roughly the first ~30 cards are in the initial HTML and the rest hydrate via lazy-load/AJAX on scroll, so a real scraper needs a headless browser or the lazy-load AJAX endpoint, not a single requests.get. Per item you get rank badge, ASIN (data-asin), title, price (EGP), star rating, review count, image, and /dp/ link. Best Sellers are advertised as "updated hourly/frequently"; Movers & Shakers ranks the biggest 24-hour sales-rank gainers and refreshes hourly. Egypt's default locale is English (en_AE) with Arabic (ar_AE) available; language is switched via the /-/en/ vs /-/ar/ URL path segment and/or Accept-Language. The hardest part is not parsing but Amazon's AWS WAF anti-bot (a raw datacenter fetch returns HTTP 503/captcha, which I reproduced live), so rotating residential IPs + realistic headers + a browser engine are required for a free/scraping strategy.


**Key findings:**
- BEST SELLERS URL: https://www.amazon.eg/gp/bestsellers (Arabic default) and https://www.amazon.eg/-/en/gp/bestsellers (English). Category form: https://www.amazon.eg/-/en/gp/bestsellers/<category-slug> — confirmed live slugs include /electronics, /beauty, /home (Home & Kitchen), /office-products. Deeper subcategory form appends a numeric browse-node id: /gp/bestsellers/<slug>/<nodeId>/ref=zg_bs_nav_<...>.
- MOVERS & SHAKERS URL: https://www.amazon.eg/gp/movers-and-shakers and English https://www.amazon.eg/-/en/gp/movers-and-shakers. Category form mirrors best sellers: /gp/movers-and-shakers/<slug>/ref=zg_bsms_nav_<slug>_0 (the zg_bsms ref token is the Movers&Shakers signature, vs zg_bs / zg_bsnr for Best Sellers). Pattern verified on amazon.com/.de/.in and amazon.eg shares the identical template.
- LOCALE/LANGUAGE (official PA-API Egypt locale ref): marketplace host www.amazon.eg; default language en_AE (English); Arabic available as ar_AE. Note Amazon uses the _AE suffix even for the EG marketplace. In-URL switch is the path segment '/-/en/' (English) vs '/-/ar/' (Arabic) immediately after the host; you can also force language with the Accept-Language request header (e.g. ar-EG or en-US). Same browse-node ids/ASINs across both languages — only title text and currency formatting localize.
- ITEMS PER LIST: 50 ranked products per category, split into 2 pages of ~50 to reach the Top 100 (Best Sellers) ; Movers & Shakers commonly shows up to ~100 as well. Pagination is via a ?pg=2 / pg=2 query param and the .a-pagination control at the bottom (ref tokens like ref=zg_bs_pg_2 / zg_bsms_pg_2).
- LAZY-LOAD BEHAVIOR (critical): the page is server-rendered HTML but only ~30 of the 50 cards are present on first load; the remaining ~20 hydrate via an AJAX/lazy-load call when you scroll to the .a-pagination area. A plain HTTP GET yields a partial list — you must either drive a headless browser (scroll + wait), or call the p13n 'aod'/zeitgeist async fragment that returns the rest.
- PRODUCT CARD CONTAINER: top-level grid is div.p13n-desktop-grid (also seen as a div[data-client-recs-list] / role=list). Each card root is div#gridItemRoot (id repeated per item) wrapping div.a-cardui ... .p13n-grid-content. An alternate/older container class is .zg-no-numbers / .zg-item-immersion. Iterate gridItemRoot elements; card index (1-based, offset by page) gives rank as fallback.
- FIELD SELECTORS (verbatim, current 2025-26): RANK badge = span.zg-bdg-text (text like '#1'); ASIN = the data-asin attribute on a child div (e.g. div[data-asin]); TITLE = div._cDEzb_p13n-sc-css-line-clamp-3_g3dy1 (clamp class; the trailing hash _g3dy1 is build-volatile — match by prefix div[class*='p13n-sc-css-line-clamp'] or the a-link-normal text); PRICE = span._cDEzb_p13n-sc-price_3mJ9Z or robustly span[class*='p13n-sc-price'] (value in EGP, e.g. 'EGP 1,299.00' / 'ج.م'); RATING = i[class*='a-icon-star'] then read the sibling/parent a[aria-label] or span.a-icon-alt text (e.g. '4.5 out of 5 stars'); REVIEW COUNT = the a-size-small link text near the stars (parsed from the same a-icon-alt aria-label or span.a-size-small a); IMAGE = img src/srcset inside the card; URL/ASIN link = a.a-link-normal[href*='/dp/'] (extract /dp/<ASIN>).
- ANTI-BOT REALITY (verified live): a direct datacenter fetch of https://www.amazon.eg/-/en/gp/bestsellers/electronics returned HTTP 503 Service Unavailable. Amazon fronts these pages with AWS WAF + 'Robot Check'/captcha. Free strategy must use rotating residential/mobile IPs, a real browser User-Agent, Accept-Language, cookies (i18n-prefs/session), human-like pacing, and ideally a headless browser (Playwright/Selenium) rather than requests/httpx.
- REFRESH CADENCE: Best Sellers pages are described by Amazon as updated 'hourly'/'frequently' (BSR underneath updates roughly hourly; the curated list visibly turns over multiple times/day). Movers & Shakers = 'biggest gainers in sales rank over the past 24 hours', recomputed hourly. Practical scrape cadence: hourly for Movers & Shakers, every 1-3h for Best Sellers; no value polling faster than ~hourly.
- EMBEDDED JSON: there is NO single clean JSON blob for the whole list. Data is primarily in the rendered HTML attributes/classes above. However each card carries machine-readable hooks: data-asin, data-client-recs-list / data-a-* attributes, and the lazy-load fragment is fetched as an HTML partial (not pure JSON). Parse HTML (BeautifulSoup/lxml/parsel) rather than expecting a JSON API. ASIN + image CDN urls (m.media-amazon.com/images/I/<id>.jpg) are reliably embedded.
- CATEGORY / BROWSE-NODE TREE: top categories are reachable by human-readable slug (electronics, beauty, home, office-products, fashion, grocery, toys, books, etc.) shown in the left rail; drilling into a subcategory swaps to a numeric browse-node id in the path (/gp/bestsellers/<slug>/<nodeId>/). Best way to enumerate the tree for free is to scrape the left-sidebar <a> links on each bestsellers page recursively (each link is /gp/bestsellers/<slug-or-node>/ref=zg_bs_nav_<depth>_<parent>) — node ids are not publicly published for .eg, so harvest them from the live nav rather than hardcoding.
- FIELDS NOT ON THE LIST PAGE: full BSR number, brand, seller, stock status, variations, and exact price history are NOT in the list card — only the snapshot rank, title, price, rating, review count, image, ASIN. To enrich, follow the /dp/<ASIN> link (separately rate-limited). amazon.eg prices show in Egyptian Pound (EGP / ج.م).


**Egypt specifics:** amazon.eg is the live Egypt storefront (ex-Souq.eg), running on the shared Amazon MENA platform — its Best Sellers/Movers pages render from the same p13n template as amazon.ae, and the page <title> literally reads 'amazon.ae Best Sellers...' even on .eg URLs (do not treat that as a wrong-domain bug). VERIFIED: host www.amazon.eg; default language en_AE, Arabic ar_AE available; English path '/-/en/', Arabic via default or '/-/ar/'. Live Best Sellers category slugs that resolve on .eg: /electronics, /beauty, /home, /office-products (and a 'best-seller' search at /-/en/best-seller/s?k=best+seller). Prices are in EGP (ج.م). A direct (non-residential) GET of an amazon.eg bestsellers URL returned HTTP 503 today, confirming the same AWS WAF anti-bot as other Amazon TLDs. NOT INDEPENDENTLY VERIFIED for .eg specifically: the exact numeric browse-node IDs (harvest from live nav), whether every category is populated (smaller catalog than .com, some lists may show <50 items), and the precise lazy-load fragment URL on .eg (assume same p13n async endpoint as .com/.ae).


**Implementation notes:** FETCH: Use a headless browser (Playwright/Selenium) per category URL; set realistic User-Agent + Accept-Language (en-US,en;q=0.9 or ar-EG,ar;q=0.9), seed cookies (session-id, i18n-prefs={'currency':'EGP'}), and ROTATE residential/mobile IPs (datacenter IPs get 503/captcha — reproduced). To get all 50 items: page.goto(url) -> scroll to selector '.a-pagination' -> wait ~3s for lazy cards -> then read DOM; OR capture the p13n lazy-load XHR in devtools and replay it. PAGINATE by appending '?pg=2' (or following the .a-pagination 'next' link) for ranks 51-100. \nPARSE (BeautifulSoup/parsel): iterate items = soup.select('div#gridItemRoot') (fallback 'div[id=gridItemRoot]', or '.p13n-desktop-grid .a-cardui'). Per item: rank = item.select_one('span.zg-bdg-text') text -> strip('#') (fallback = enumerate index + 50*(page-1)); link = item.select_one(\"a.a-link-normal[href*='/dp/']\"); asin = item.select_one('div[data-asin]')['data-asin'] OR regex r'/dp/([A-Z0-9]{10})' on href; title = item.select_one(\"div[class*='p13n-sc-css-line-clamp']\").get_text(strip=True); price = item.select_one(\"span[class*='p13n-sc-price']\") text -> strip 'EGP'/'ج.م', parse float; rating = item.select_one('span.a-icon-alt') text -> regex r'([0-9.]+) out of 5' (or the parent a[aria-label]); reviews = item.select_one('a.a-size-small, span.a-size-small') text -> digits; image = item.select_one('img')['src'] (or parse 'srcset'). \nMOVERS&SHAKERS extra field: percentage/rank-gain badge sits in the same card area (text like '+1,234%' or 'was #X'); capture the zg_bsms ref and the gain text. \nSCHEDULE: cron hourly for /gp/movers-and-shakers, every 1-3h for /gp/bestsellers; jitter requests, respect ~hourly data refresh, cache by (category, lang, page). \nTREE DISCOVERY: BFS the left-rail links soup.select(\"a[href*='/gp/bestsellers/']\") starting from the root /gp/bestsellers, dedupe by node-id/slug, persist the mapping {slug/nodeId -> name, parent}. \nSTORAGE: key rows by (snapshot_ts, list_type, category_node, lang, rank, asin). Robust selectors should match by class PREFIX (the trailing hashes like _3mJ9Z/_g3dy1 change on Amazon redeploys). Always keep the enumerate-index rank fallback. Respect robots.txt/ToS — this is the legal/ToS risk, not a technical one.


**Not verified:** Exact numeric browse-node IDs for amazon.eg categories/subcategories (not published; must be harvested from the live left-nav at scrape time).; Whether amazon.eg populates a full 50/100 items in every category — smaller Egypt catalog may yield short lists in niche categories (could not load live page; got 503).; The precise amazon.eg lazy-load/AJAX fragment URL for cards 31-50 (assumed identical to the .com/.ae p13n async endpoint, not directly observed on .eg).; Whether '/-/ar/' is the exact Arabic path token on .eg (Arabic confirmed available as ar_AE via PA-API; the '/-/en/' English prefix is confirmed live, Arabic prefix inferred by symmetry).; Current build-hash class suffixes (e.g. _3mJ9Z, _g3dy1) — these rotate on Amazon front-end deploys; verified from 2024-25 guides, may differ today, hence match by class prefix.; Could not fetch a live amazon.eg list page end-to-end (HTTP 503 from datacenter IP), so per-field selectors are cross-validated from scraping guides (.com/.ae template) rather than confirmed on .eg HTML directly.; Exact per-category refresh interval on .eg (Amazon states hourly/24h globally; .eg may refresh less often due to lower traffic).


## Amazon Egypt (amazon.eg) search autocomplete/suggestions endpoint as a FREE demand proxy for "most searched" queries

*Confidence: medium*

Amazon exposes an undocumented public autocomplete endpoint at https://completion.amazon.com/api/2017/suggestions that powers the search-box dropdown across all marketplaces, including Amazon Egypt. For Egypt you pass the marketplace ID mid=ARBP9OOSHTCHU (country code EG, verified against Amazon SP-API docs), alias=aps (All Product Search), and prefix=<query>; the endpoint returns clean JSON with a top-level "suggestions" array. The live endpoint accepts the Egypt mid and returns valid JSON (correct alias/prefix echo + responseId), and it supports both Latin and Arabic prefixes. By iterating seed letters/prefixes ("a".."z", "0".."9", and "iphone ", "samsung " + each next letter), you harvest the ranked completions Amazon serves — these are an ESTIMATED-DEMAND / popularity proxy (Amazon orders them by what shoppers commonly type), NOT true search volume; there are no published counts. A documented stress test hit the same endpoint 4,000+ times with no rate limiting observed, so it is viable for a free/scraping strategy, though Amazon's HTML search-results pages (amazon.eg/s?k=) actively block plain bots (503).


**Key findings:**
- ENDPOINT (current): GET https://completion.amazon.com/api/2017/suggestions — the modern Amazon autocomplete API powering the search-box dropdown. Returns JSON. The older host path https://completion.amazon.com/search/complete now returns HTTP 404 (deprecated for this use).
- EGYPT MARKETPLACE ID: mid=ARBP9OOSHTCHU (country code EG), verified on the official Amazon SP-API 'Marketplace IDs' page (developer-docs.amazon.com/sp-api/docs/marketplace-ids). For comparison: SA=A17E79C6D8DWNP, UAE=A2VIGQ35RCS4UG, US=ATVPDKIKX0DER.
- MINIMAL WORKING REQUEST for Egypt: https://completion.amazon.com/api/2017/suggestions?mid=ARBP9OOSHTCHU&alias=aps&prefix=iphone . Required params: mid, alias (use 'aps' = All Product Search), prefix (the typed letters). Verified live: returns HTTP 200 + valid JSON echoing the alias/prefix and a unique responseId for the Egypt mid.
- LANGUAGE (Arabic vs English): pass lop=ar_EG for Arabic results or lop=en_AE/en_US-style for English; the prefix itself can be Arabic (URL-encoded UTF-8, e.g. prefix=ايفون for 'iphone'). Egypt's storefront is bilingual (Arabic default, English via /-/en/). lop = 'language of product'/locale.
- JSON RESPONSE SHAPE (verified live, top level): { "alias":"aps", "prefix":"iphone", "suffix":null, "suggestions":[...], "predictiveText":null, "suggestionTitleId":null, "responseId":"<id>", "shuffled":false }. The harvestable data is the ordered 'suggestions' array.
- SUGGESTION OBJECT FIELDS (per the completion.amazon.com gist documentation): each entry includes value (the suggested query STRING — this is what you collect), type (e.g. 'KEYWORD'), prior, refTag (Amazon ref tag), strategyId, ghost, plus optional help/isFallback. The ordering of the array is the popularity ranking = the demand signal.
- SEED-LETTER / ALPHABET EXPANSION (the harvesting method): for each seed term append a space + every char a–z and 0–9 (e.g. 'iphone a','iphone b'...'iphone z','iphone 0'...'iphone 9'), and also iterate bare single letters 'a'..'z'. PEMAVOR documents this expands ~10 results/query to ~350 unique suggestions per seed. Recursively expanding top suggestions builds a ranked query corpus.
- OPTIONAL PARAMS (from gist): limit (max suggestions, ~10–11 default), suggestion-type=KEYWORD (also WIDGET/PRODUCT variants exist), client-info=amazon-search-ui, session-id, customer-id, request-id, page-type=Gateway, site-variant, b2b=0|1, fresh, event=onKeyPress, and a cache-buster timestamp param (_=<epoch_ms>).
- RATE LIMITS: No official limit published and none documented as enforced. A public write-up (Medium 'To kill a mocking search') fired 4,000+ requests at /api/2017/suggestions with no rate limiting hit. Treat as soft — self-throttle (e.g. 1–3 req/s, rotate User-Agent, add jitter) to avoid IP blocks.
- DEMAND-PROXY CAVEAT (critical): suggestions are an ESTIMATED popularity/demand proxy. Amazon ranks completions by aggregate shopper typing behavior, but exposes NO numeric volume. There is no true 'search volume' number — only ordinal rank (array position) and presence/absence. Frequency of a term surfacing across many seed expansions can be used as a relative-demand score.
- AMAZON.EG SEARCH-RESULTS PAGE (HTML) is the second data source but is bot-protected: plain fetch of https://www.amazon.eg/-/en/s?k=iphone returned HTTP 503 (and amazon.eg/s?k= similar). Scraping needs real browser headers / headless browser / rotating proxies; the suggestions JSON endpoint is far more scrape-friendly than the SERP HTML.
- AMAZON.EG SERP FIELDS PER RESULT (standard Amazon DOM, to target once rendered): container div[data-component-type="s-search-result"] with data-asin="<ASIN>"; title in h2 a span (or h2 .a-text-normal); price in span.a-price > span.a-offscreen (and a-price-whole/a-price-fraction); rating in span.a-icon-alt ('4.3 out of 5 stars'); review count in a span next to rating (e.g. a-size-base.s-underline-text); thumbnail img.s-image; sponsored items flagged by an 'a-sponsored-label-text' / 'Sponsored' badge; result rank by DOM order.


**Egypt specifics:** amazon.eg marketplace ID = ARBP9OOSHTCHU (country EG), confirmed on Amazon's official SP-API Marketplace IDs page. The completion endpoint accepts this mid and returns valid JSON (verified live: correct alias/prefix echo + responseId for both a Latin prefix 'iphone' and an Arabic prefix 'ايفون'). Egypt is bilingual: use lop=ar_EG (Arabic, the default storefront language) and an English locale for the /-/en/ storefront; Arabic prefixes must be UTF-8 URL-encoded. The amazon.eg HTML SERP (https://www.amazon.eg/-/en/s?k=) is bot-blocked (503 to plain requests), so the suggestions JSON endpoint is the practical free channel for Egypt demand harvesting. Currency on SERP is EGP (ج.م). Note: in the live tests the suggestions array came back empty via a server-side fetcher lacking a browser User-Agent/session — in production send a browser-like User-Agent (Mozilla/5.0...), include a session-id and the cache-buster _=<epoch> param, and optionally a referer of amazon.eg to get populated suggestions (the empty array is a client/anti-automation artifact, not a sign the mid is unsupported, since the responseId/echo confirm Egypt routing works).


**Implementation notes:** BUILD A DEMAND-PROXY HARVESTER: 1) Base call (Python requests): URL='https://completion.amazon.com/api/2017/suggestions'; params={'mid':'ARBP9OOSHTCHU','alias':'aps','prefix':seed,'lop':'ar_EG' (or en),'limit':11,'suggestion-type':'KEYWORD','client-info':'amazon-search-ui','_':int(time.time()*1000)}; headers={'User-Agent':'Mozilla/5.0 (...) Chrome/124 Safari/537.36','Accept':'application/json','Referer':'https://www.amazon.eg/'}. Parse r.json()['suggestions']; collect each obj['value'] (the query) keeping array index as ordinal rank. 2) SEED STRATEGY: Pass A = single chars a–z, 0–9, plus common Arabic letters (ا ب ت ...). Pass B = for each high-value collected term t, expand 't '+char for char in [a-z,0-9]. Pass C (recursive, depth 2–3): re-expand newly discovered top terms. Dedupe; this yields hundreds–thousands of unique ranked queries (~350 per seed per PEMAVOR). 3) SCORING (since no real volume): demand_score(query) = function of (best/avg array rank across all expansions where it appeared) + (count of distinct prefixes that surfaced it). Lower mean-rank and higher appearance-frequency => higher estimated demand. Store {query, lang, min_rank, appearances, first_seen_date} and snapshot daily/weekly to build a TREND time-series (rising rank = rising demand). 4) THROTTLING/RESILIENCE: 1–3 req/s with random jitter, rotate User-Agent, optionally rotate egress IP; backoff on non-200; cache 15 min. 5) OPTIONAL SERP ENRICHMENT (for each top query, scrape amazon.eg/-/en/s?k=<query> via headless browser due to 503 on plain fetch): extract per-result div[data-component-type='s-search-result'] data-asin, h2 a span (title), span.a-price span.a-offscreen (price EGP), span.a-icon-alt (rating), review count, img.s-image, and Sponsored flag to map demand-queries to actual ASINs/prices. 6) ALWAYS LABEL OUTPUT as 'estimated demand proxy (autocomplete-derived), not true search volume.'


**Not verified:** Whether the LIVE suggestions array populates with real Egypt queries from a proper browser session — my server-side fetches returned a structurally-valid but EMPTY suggestions array (likely missing browser User-Agent/session/anti-automation), so the exact populated suggestion objects for Egypt were not directly observed.; The precise current field names inside each populated suggestion object for amazon.eg specifically (value/type/refTag/prior/strategyId/ghost are from gist documentation of completion.amazon.com generally, not confirmed against a live non-empty Egypt response).; Exact rate-limit thresholds and any IP-ban behavior for amazon.eg/Egypt mid — only the absence of throttling in one third-party stress test is documented; Amazon may throttle or block in 2026.; Whether lop=ar_EG vs another locale string (e.g. ar_AE) is the canonical Egypt Arabic value, and whether a separate Egypt-specific completion host exists.; Live amazon.eg SERP DOM selectors were NOT directly inspected (page returned 503); listed selectors are the standard Amazon SERP structure and may differ slightly on amazon.eg.; Whether 'suggestions' ordering is strictly popularity-ranked vs personalized/blended when session-id/customer-id are supplied.


## amazon.eg Product Detail + Reviews — scrape target mapping (FREE/scraping strategy, no paid data APIs)

*Confidence: medium*

amazon.eg uses the standard Amazon URL scheme with an inserted language segment: product detail = https://www.amazon.eg/-/en/dp/{ASIN} (Arabic default = https://www.amazon.eg/dp/{ASIN}); reviews = https://www.amazon.eg/-/en/product-reviews/{ASIN}. ASIN is the canonical 10-char key (e.g. B0DGHYDZHB). Product pages expose title, price (EGP), brand, average rating, total review count, rating histogram, seller/sold-by, availability and Best Sellers Rank via stable id/data-hook selectors shared across all Amazon locales. Reviews carry star, title, body, date, verified-purchase badge, helpful votes and reviewer name via data-hook attributes. The hard constraints for a free strategy: review pagination is capped (historically 10 pages x 10 = 100 reviews; Amazon reduced this to ~5 pages / ~50 in late 2024 for logged-out users), star/sort filters multiply the reachable set to ~300-500, and a growing share of full review data is now login-gated. Direct datacenter fetches of amazon.eg returned HTTP 503 in my testing, so residential proxies + a real/headless browser and Arabic+English locale handling are required.


**Key findings:**
- URL — product detail: `https://www.amazon.eg/-/en/dp/{ASIN}` (English) or `https://www.amazon.eg/dp/{ASIN}` (Arabic, the marketplace default). The `/-/en/` path segment is amazon.eg's language switch; both resolve to the same ASIN. Canonical/short form `/dp/{ASIN}` is preferred over legacy `/gp/product/{ASIN}`. ASIN is a 10-char alphanumeric (e.g. B0DGHYDZHB).
- URL — reviews: `https://www.amazon.eg/-/en/product-reviews/{ASIN}/` with query params: `pageNumber={1..N}`, `sortBy=recent|helpful`, `reviewerType=all_reviews|avp_only_reviews` (avp_only = verified-purchase only), `filterByStar=one_star|two_star|three_star|four_star|five_star|positive|critical`, `formatType`, `mediaType=media_reviews_only`, plus `language=en_AE`/`ar_AE` to force locale and `&pageSize` (default 10).
- Product-page selectors (same across Amazon locales incl .eg): title `#productTitle`; price `#corePriceDisplay_desktop_feature_div span.a-price span.a-offscreen` (fallbacks `.priceToPay .a-offscreen`, `.apexPriceToPay .a-offscreen`, `.a-price-whole`+`.a-price-fraction`); brand `#bylineInfo` (or the 'Brand' row in `#productOverview_feature_div` / `tr.po-brand td.a-span9`); availability `#availability span`, out-of-stock `#outOfStockBuyBox_feature_div`.
- Rating + review count selectors: average star `#acrPopover .a-icon-alt` or `i[data-hook=average-star-rating] .a-icon-alt` (text like '4.3 out of 5 stars'); total review count `#acrCustomerReviewText` or `div[data-hook=total-review-count]` (e.g. '1,234 ratings'). Parse the float with regex `(\d+[.,]?\d*)\s*out of`.
- Rating histogram (per-star %): table `#histogramTable` / `#cm_cr_dp_d_rating_histogram`; each row `a[data-hook=histogram-row]` or `.a-histogram-row`, with the star label in `.a-text-left` and the percentage in `.a-text-right .a-size-base` (e.g. '62%'). On newer layouts the bars are in `#cr-summarization-attributes-list` / `[data-hook=cr-roll-up-reviews]`.
- Seller / sold-by: `#sellerProfileTriggerId` (seller display name, links to `/sp?seller={SELLER_ID}`) and `#merchant-info`; ships-from/sold-by also in the buy-box `#tabular-buybox` rows and in the All-Offers-Display panel (`#aod-offer-soldBy`, `#aod-offer-shipsFrom`, `#aod-offer-seller-rating`). Seller ID is the load-bearing field for joining.
- Best Sellers Rank (BSR): not a clean id — extract from the Product Information / detail block. Two layouts: (a) `#productDetails_detailBullets_sections1` table — find the `<th>` containing 'Best Sellers Rank' and read its `<td>`; (b) `#detailBulletsWrapper_feature_div #detailBullets_feature_div li` — find the `<li>` whose text contains 'Best Sellers Rank'. Regex `#([\d,]+)\s+in\s+([^(]+)` to get rank + category. amazon.eg shows BSR in English even on Arabic pages for many categories, but BSR is frequently absent on .eg listings (Not verified per-category).
- Per-review selectors (data-hook based, stable across locales): container `div[data-hook=review]` (id = the review id); reviewer name `.a-profile-name`; star rating `[data-hook=review-star-rating] i.a-icon-alt` or `[data-hook=cmps-review-star-rating]` (text 'X out of 5 stars'); title `[data-hook=review-title] span` (last span = title text, since first spans may hold the rating); body `[data-hook=review-body] span`; date+country `[data-hook=review-date]` (e.g. 'Reviewed in Egypt on 12 March 2026'); verified badge `[data-hook=avp-badge]` (text 'Verified Purchase'); helpful votes `[data-hook=helpful-vote-statement]` ('3 people found this helpful').
- Pagination LIMIT (critical for free strategy): logged-out pagination is capped — historically 10 pages x 10 reviews = 100; Amazon reduced visible pages to ~5 (≈50 reviews) for unauthenticated users from ~Sep 2024. The 'Next page' link `.a-pagination .a-last > a` becomes disabled (`.a-last.a-disabled`) past the cap. Workaround WITHOUT paying: iterate the star filters (`filterByStar=one_star..five_star`) and both `sortBy=recent` and `helpful`, each returning its own ≤~50-100 set → ≈300-500 distinct reviews reachable for free.
- LOGIN WALL (verified, growing): Amazon increasingly gates full review access behind authentication. ## Defensible "most-selling / rising / estimated-demand" metrics from FREE scraped data (BSR snapshots + autocomplete) for Amazon Egypt (amazon.eg)

*Confidence: medium*

On a no-paid-API budget, the two scrapable signals that carry real demand information on amazon.eg are (1) Best Sellers Rank (BSR), shown per-product and on the live /gp/bestsellers and /gp/movers-and-shakers list pages, and (2) search autocomplete suggestions from Amazon's completion API. BSR is a relative, category-specific popularity rank (lower = more recent unit velocity, recalculated ~hourly); converting it to absolute units requires a category-calibrated power-law (Daily Sales ≈ A·BSR^B) that is only roughly accurate and that you CANNOT calibrate properly for Egypt without ground-truth, so treat BSR primarily as an ordinal rank, not a unit count. "Rising" is best derived yourself by snapshotting BSR over time and computing rank-velocity (the same logic Amazon's Movers & Shakers uses: percentage rank improvement vs ~24h ago), which needs no sales model and is the most defensible signal you have. "Estimated demand" for keywords should be a 0-100 score from autocomplete prefix-expansion (does the term surface, and how high in the list, across progressively longer prefixes) blended with the BSR of the products that term surfaces — never presented as a search-volume number. The whole product must visibly disclose that these are relative, modeled estimates with wide error bars, especially because amazon.eg is a thin marketplace where ranks are noisy.


**Key findings:**
- BSR-to-sales is a power law: Daily Sales ≈ A × BSR^B. Published consumer-tool coefficients (Books, recalibrated Nov 2025): BSR 100-999 → A=31,622.78, B=-0.7781; BSR 1,000-99,999 → A=25,920, B=-0.778151; BSR 100,000+ → A=9,331.2, B=-0.778151. Sanity points: BSR #100 ≈ 1,000/day, #10,000 ≈ 20/day, #100,000 ≈ 1.2/day. These are BOOKS-specific and NOT valid for electronics/home — use only as a shape, not Egypt truth (bookbloom.io).
- Category is the dominant error source: the SAME BSR of 100,000 ≈ 150-200 sales/mo in Books but only 30-40/mo in Home & Kitchen — a ~5x spread. There is no single cross-category formula; any sales number must be category-scoped, and you have no amazon.eg ground truth to fit B/A, so absolute unit claims for Egypt are 'Not verified' by construction.
- Stated accuracy of even calibrated US/book models is ±10-15% at ranks 1-1,000, ±15-20% at 1k-10k, ±20-25% at 10k-100k, and worse beyond — and that is WITH proprietary calibration data you won't have for Egypt. Treat any displayed unit estimate as an order-of-magnitude band, not a point value (amzprep.com, easyparser.com).
- Amazon Movers & Shakers is computed as PERCENTAGE rank improvement vs ~24h ago, updated ~hourly, per category — e.g. rank moved 30→10 = 200% gain. It measures momentum/velocity, NOT absolute volume, so a 30/day product can outrank a 200/day product. This is exactly the 'rising' metric and you can reproduce it from your own BSR snapshots without any sales model (amazon.com/gp/movers-and-shakers).

- Amazon autocomplete uses a public completion API. Canonical shape: https://completion.amazon.eg/api/2017/suggestions?prefix=...&alias=aps&mid=<EG_marketplace_id>&... returning JSON {alias, prefix, suffix, suggestions:[...], responseId, shuffled}. A wrong/missing mid yields an empty suggestions array (observed), so the Egypt marketplace id must be captured from a real browser session.
- Autocomplete demand-scoring heuristic (open-source MrXavier/amazon-autocomplete-keyword-score): for a target phrase, query each successive prefix ('i','ip','iph',...) and find the first prefix at which the full phrase appears and its INDEX in the returned list. Score starts at 100, is apportioned by prefix length, and is reduced by suggestion position (full credit at top, ~50% mid-list, near-zero at bottom); if the phrase is the #1 suggestion at an early prefix, stop early = max score. Net: terms that surface early (short prefix) AND high (low index) score highest.
- Seed expansion for breadth: take each seed (category name, brand, top product noun) and append a-z / 0-9 (and common Arabic letters for the ar locale) as suffixes, harvest all returned suggestions, dedupe, then recurse one level on the most frequent stems. Frequency = how many distinct seed+letter queries surface a given suggestion; this co-occurrence count is a defensible relative-popularity proxy (the 'demand frequency') WITHOUT any volume number.
- Snapshot cadence drives every window: capture BSR at a FIXED hour daily (Amazon recalcs ~hourly, so same-time sampling removes intraday phase noise). Daily risers = Δ over 1 snapshot; weekly = 7-snapshot trend/slope; monthly = ~30-snapshot trend. To approximate Amazon's own hourly Movers & Shakers you'd need hourly captures, but 1-4×/day is a realistic free-tier compromise. Keep a rolling 90-day history for trend/seasonality and to compute medians that suppress single-snapshot spikes.
- Rank velocity is more robust than modeled units: rank improvement % over 24h = (BSR_prev − BSR_now)/BSR_prev. Because BSR is heavy-tailed, ALWAYS smooth in log space (use Δlog(BSR) = ln(BSR_prev) − ln(BSR_now)) and rank risers by that; a positive Δlog means improving. This is the single most defensible 'rising' metric and mirrors M&S without claiming unit counts.
- amazon.eg is a comparatively THIN marketplace: many sub-categories have few competing ASINs, so BSR is volatile and a handful of sales can swing rank dramatically. This AMPLIFIES uncertainty vs amazon.com — small-sample noise must be disclosed, low-data categories flagged, and single-snapshot 'spikes' down-weighted vs sustained multi-day trends.

Respect robots/ToS and rate-limit — this is scraping, not an API entitlement.

- Ready-to-use Arabic snippet (no training): `from transformers import pipeline; sa = pipeline('text-classification', model='Ammar-alhaj-ali/arabic-MARBERT-sentiment'); sa(['لقد استمتعت بالحفلة','خدمة المطعم كانت محبطة'])` returns label+score (e.g. positive 0.958, negative 0.916).
- AraBERT (aubmindlab/bert-base-arabertv2) is the other major free Arabic encoder; strong on MSA, slightly weaker than MARBERT on heavy dialect. Good fallback / ensemble member. PRAli22/AraBert-Arabic-Sentiment-Analysis is a ready sentiment fine-tune. 2025 RANLP AHaSIS shared task confirms transformer fine-tunes (AraBERT/MARBERT) are SOTA for Arabic-dialect sentiment.
- CAMeL Tools (github.com/CAMeL-Lab/camel_tools, NYU Abu Dhabi, MIT) = all-in-one free Arabic toolkit: preprocessing/normalization, morphology, DIALECT IDENTIFICATION, NER, and a sentiment analyzer (pos/neg/neutral). Pip-installable; has CLI + Python API. Best used for normalization + dialect-ID, not as the final sentiment model.
- CAMeLBERT-DA sentiment (CAMeL-Lab/bert-base-arabic-camelbert-da-sentiment) is BERT-base (~110M), fine-tuned on ASTD+ArSAS+SemEval, but only BINARY (positive/negative) and benchmarks show it underperforms MARBERT/AraBERT on dialectal sentiment. Very popular (~145k downloads/mo) but not the accuracy leader. Snippet: `pipeline('text-classification', model='CAMeL-Lab/bert-base-arabic-camelbert-da-sentiment')`.
- EGYPTIAN-DIALECT SPECIFIC: EgyBERT (arxiv 2408.03524, 2024) is pretrained specifically on Egyptian-dialect corpora and beats general Arabic models on Egyptian tasks — strongest option if you fine-tune for amazon.eg's Masry reviews, though you must train a sentiment head (no turnkey pipeline). MARBERTv2 dialect classifier (IbrahimAmin/marbertv2-arabic-written-dialect-classifier, trained on ~850k sentences, 9 dialects incl. Egyptian) can pre-tag reviews as Egyptian vs MSA.
- DIALECT CHALLENGE (the core risk): amazon.eg reviews mix (a) MSA, (b) Egyptian colloquial 'Masry', (c) Franco-Arabic/Arabizi in Latin letters ('el-product da 3agbni gdn', 'msh helw', 'wesel bsor3a'), (d) Arabic+English code-switching, (e) emoji/elongation ('حلـــــــو'), and (f) sarcasm/negation. MSA-only or English-only models silently mislabel these. Mitigations: Arabic normalization (alef/ya/ta-marbuta, diacritic + tatweel removal via CAMeL Tools), an Arabizi-to-Arabic transliteration step, and a dialect-pretrained model.
- SENTIMENT (English reviews on amazon.eg): use a small CPU model. distilbert-base-uncased-finetuned-sst-2-english = ~91.3% SST-2 acc, 40% smaller/faster than BERT, binary pos/neg. cardiffnlp/twitter-roberta-base-sentiment-latest = 3-class (neg/neu/pos), trained on ~124M tweets, better on short informal review text. VADER (lexicon, NLTK) is ~83% but instant/zero-model — good cheap pre-filter, weak on nuance.
- ENGLISH lexicon fallbacks: VADER (vaderSentiment / NLTK, free) and TextBlob are rule/lexicon-based, no GPU, handle emoji/punctuation/caps emphasis; accuracy lower (~80-83%) than transformers. Best role: ultra-cheap first pass or for tie-breaking, not primary scoring.
- THEME / KEYWORD EXTRACTION (free): KeyBERT (github.com/MaartenGr/KeyBERT, MIT) extracts keyphrases via embeddings; for Arabic+English use multilingual embeddings (paraphrase-multilingual-MiniLM-L12-v2). Reported ~80.95% on Arabic keyword extraction vs ~81-82% for AraBERT variants. Use MMR + ngram_range=(1,3) + Arabic & English stopword lists to get clean 'battery life', 'عمر البطارية', 'shipping', 'الشحن' phrases.
- RECURRING-THEME clustering (free): BERTopic (also MaartenGr) on multilingual sentence embeddings clusters thousands of reviews into topics (delivery, price, quality, fake/original, sizing) and gives representative keywords per cluster — ideal for 'recurring themes per product/category'. For a single product with few reviews, skip BERTopic and just use KeyBERT keyphrase frequency.
- PROS/CONS + COMPLAINT SUMMARY (free, extractive — avoid paid LLM): split reviews by predicted sentiment, run KeyBERT on the positive set -> top phrases = PROS, on the negative set -> top phrases = CONS/complaints, then pick the most representative actual sentences per phrase as evidence quotes. This is deterministic, cheap, bilingual, and needs no generative model. Optional free abstractive upgrade: a small mT5/AraT5 summarizer, but it raises runtime cost.
- ASPECT-BASED option: map keyphrases to fixed aspect buckets (Quality, Price/Value, Shipping/Delivery, Authenticity/Counterfeit, Packaging, Seller/Service, Battery, Sizing) and compute per-aspect sentiment by averaging sentiment of sentences containing each aspect's terms (bilingual lexicon). Gives a structured per-product pros/cons table without ML aspect extractors.
- RESOURCE / RUNTIME: All weights are free + downloadable. BERT-base/MARBERT/AraBERT ~110M params -> ~420-500MB on disk, ~1-2GB RAM; run on CPU. DistilBERT ~66M is ~2x faster. CPU throughput roughly tens to low-hundreds of reviews/sec batched (GPU optional, 10-50x). KeyBERT/BERTopic embeddings (MiniLM, ~80-120MB) are the lightweight part. VADER/TextBlob are near-instant, negligible memory. Whole stack fits on a free-tier/small VPS; only cost is CPU time + ~1-2GB model storage.


**Egypt specifics:** amazon.eg reviews are overwhelmingly Egyptian-context: a mix of Modern Standard Arabic, Egyptian colloquial 'Masry', Franco-Arabic/Arabizi written in Latin letters and digits ('3', '7', '2' for Arabic letters, e.g. '3ayez', 'msh 7elw', 'wesel bsor3a'), Arabic-English code-switching, plus English-only reviews. No amazon.eg-specific public sentiment benchmark was found (Not verified); validate on a small hand-labeled sample of real amazon.eg reviews before trusting class accuracy.

## Legal/ToS risk of scraping amazon.eg public pages for personal product-sourcing (free/no-paid-API strategy)

*Confidence: medium*

Scraping amazon.eg public product pages for your own private sourcing decisions is a low-to-moderate, primarily contractual (not criminal) risk in practice, provided you stay logged out, rate-limit hard, and never republish or resell the data. The binding constraint is Amazon's Conditions of Use, which explicitly bans "any collection and use of any product listings, descriptions, or prices" and "any use of data mining, robots, or similar data gathering and extraction tools" — so scraping is a clear ToS breach even when the pages are public. Criminal/CFAA exposure for scraping logged-out public pages is weak in the US after hiQ v. LinkedIn (violating ToS alone ≠ "without authorization"), but the Nov-2025 Amazon v. Perplexity Comet dispute shows Amazon will aggressively assert CFAA + trespass the moment automation touches a logged-in account or "masquerades as human." The EU sui-generis database right is a republication/re-utilization risk, not a personal-read risk, and post-CV-Online it only bites if you extract a substantial part in a way that harms Amazon's investment. Egypt's Law 151/2020 (PDPL) is largely irrelevant to scraping prices/specs (non-personal data) and offers a natural-person personal-use exemption, but would apply if you harvest seller/reviewer personal data. Realistic enforcement against a single low-volume personal user is throttling/IP-block/account-ban, not litigation — the legal floor is "don't get sued/banned," and you control most of that with behavior.

- Amazon v. Perplexity (cease-and-desist Nov 2025 + suit over the Comet agentic browser): Amazon asserted (1) ToS breach of its 'robots, data mining' prohibition, (2) CFAA 'computer fraud' because the agent 'masquerades as human browsing' ('trespass involves code rather than a lockpick'), and (3) trespass/unfair competition. Critically this involved automation acting on a LOGGED-IN user's stored credentials — the trigger that flips a weak CFAA theory into a viable one.
- EU sui-generis database right (Directive 96/9/EC): protects a maker who made 'substantial investment' against extraction/re-utilization of a substantial part (qualitatively/quantitatively). Post CV-Online Latvia (CJEU C-762/19, 2021) the test centers on whether extraction harms the maker's ability to recoup investment — meta-search/aggregation that doesn't deprive the maker of redemption income is generally permissible. Reading pages privately is not 'extraction of a substantial part'; bulk-copying the catalog and republishing it is the risk.
- Egypt PDPL (Law No. 151/2020), in force, Executive Regulations issued 2024/2025: applies to electronically processed PERSONAL data of individuals in Egypt, requires explicit consent, and has extraterritorial reach. It is largely orthogonal to scraping prices/specs (not personal data).
- Egypt PDPL has a natural-person personal-use exemption ('data processed by a natural person for personal use') and an exception for accurate data used purely for informational purposes — both helpful for a private sourcing use case that avoids personal data.
- Egypt PDPL penalties are real but aimed at personal-data misuse: processing personal data without consent is punishable by imprisonment (not less than ~3 months) and fines of EGP 500,000–5,000,000; if harm results, imprisonment not less than 6 months and fine EGP 200,000–2,000,000; administrative fines up to ~EGP 5m. Regulator: Personal Data Protection Center under MCIT. These bite only if you harvest seller/reviewer PII, not prices.
- Governing law/venue: Amazon's Conditions of Use bind users to Amazon's chosen law/forum and reserve the right to terminate access and pursue breach remedies; the immediate real-world enforcement tool is technical (CAPTCHA, throttling, IP/device fingerprint blocking, account suspension), not a lawsuit, for low-volume personal scraping.
- Net realism: for a single personal user pulling modest volumes of public listing/price data logged-out, the dominant risk is operational (getting blocked) plus a low-probability contractual/cease-and-desist risk; criminal and database-right exposure stay low UNLESS you log in/automate an account, use heavy volume, or republish/resell the data.


**Egypt specifics:** amazon.eg serves the same global Amazon Conditions of Use and the same robots.txt family as other Amazon locales (verified: amazon.eg/robots.txt returns the standard path Disallows + named-bot blocklist; the COU 'data mining, robots' clause is Amazon-wide). Egypt-specific law: Personal Data Protection Law No. 151/2020 governs personal data of individuals in Egypt, but it (a) targets PERSONAL data, so prices/specs/availability fall outside it, (b) provides a natural-person personal-use exemption that fits a private sourcing workflow, and (c) reserves its heavy fines (EGP 0.5m–5m, plus imprisonment) for processing identifiable personal data without consent — relevant only if you scrape seller names, reviewer profiles, or other PII. No Egyptian authority has published guidance specifically blessing or prohibiting price scraping (Not verified that any amazon.eg-specific enforcement action exists). Egypt is not in the EU, so the EU sui-generis database right does not directly govern amazon.eg, though it would matter if you later redistribute data into the EU or scrape an EU Amazon locale.


**Implementation notes:** Build guardrails into the scraper itself: (1) Stay logged out — never attach Amazon account cookies/credentials; the logged-in-automation path is exactly what converted Amazon's weak CFAA theory into a live claim in the Perplexity matter. (2) Honor robots.txt programmatically: fetch and parse amazon.eg/robots.txt, and do NOT request the path families it Disallows for * (/gp/cart, /ap/signin, /gp/wishlist/, /gp/video/library, most /-/ except /-/en/). (3) Do NOT send a recognized scraper/AI user-agent (Scrapy default, ClaudeBot, GPTBot, PerplexityBot, etc.) — those sit in an explicit Disallow:/ block; use a plain browser-like UA but don't forge it to impersonate a specific human session. (4) Rate-limit aggressively: single-threaded, randomized delays (aim seconds-per-request, e.g. 5–15s jitter), low daily volume, exponential backoff on 503/429/CAPTCHA, and stop on block rather than rotating aggressively to evade. (5) Scope the fields to non-personal commercial facts only — ASIN/title/price/availability/rating-count — and skip seller legal names, reviewer handles, Q&A author data (keeps you clear of Egypt PDPL and GDPR). (6) Treat scraped data as a private cache for your own decisions: store locally, set a short TTL, and never republish, resell, redistribute, or expose raw Amazon content via an API/app (this is the line the EU database right and COU 'resale/commercial use' clause actually defend). (7) Keep a 'good-citizen' kill switch: if Amazon serves a CAPTCHA wall or you receive any notice/cease-and-desist, stop rather than escalate evasion. (8) Document intent (personal sourcing, non-commercial) to support the personal-use posture under Egypt PDPL.
